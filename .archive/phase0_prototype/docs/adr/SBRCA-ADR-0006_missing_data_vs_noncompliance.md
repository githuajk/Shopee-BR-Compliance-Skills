# SBRCA-ADR-0006 缺失数据不等于合规：未评估项必须显式上报

| 字段 | 值 |
|---|---|
| 决策编号 | `SBRCA-ADR-0006` |

| 相关 | 章程 §5.2「必须明确哪些数据属于正式事实、风险线索、待核实记录」；`REQ-DATA-006`；`SBRCA-P1-002` §3.3 |

## 背景

第一阶段原型在合成导出（15 条商品）上的**第一版结果**：

```
products reviewed : 15
products flagged  : 15     ← 100% 判违规
```

原因是三条规则写着「无图片 → 违规 [606]」「无类目 → 违规 [613]」「无品牌 → 违规 [301]」，而那个 xlsx **根本没有图片列、类目列、品牌列**。

这是**输入数据缺失**，不是**listing 违规**。但引擎把两者混同了 —— 这是最危险的一类误报：它会让人对整个系统的信任归零。

## 可选方案

| 方案 | 说明 |
|---|---|
| A | 保持原样：缺字段 = 违规 | 危险误报 |
| B | 缺字段 = 通过（不产生发现） | **沉默的漏检** —— 运营以为检查过了 |
| C | 缺字段 = 未评估：不产生发现，但**必须**在结果与报告中可见 |

## 评估标准

误报风险；漏检可见性；运营负担；实现复杂度。

## 最终选择

**方案 C**。

机制：
1. 规则的触发条件可声明 `requires_input: ["image"]` —— 该条件依赖的输入字段。
2. 若输入中该字段不存在，条件**不评估**，不产生 finding。
3. 审核结果新增 `errors` 条目（`stage: "rule_evaluation"`，`severity: "warning"`），说明「规则 X 未评估：输入未携带字段 Y」。
4. 报告有**独立小节**展示未评估项 —— 与「通过」明确区分。
5. 规则若**不声明** `requires_input`，则其条件对缺失字段按语义正常求值（如 `field_missing` 明确表示「期望有但没有」）。

## 选择理由

1. 方案 A 制造危险误报；方案 B 制造沉默漏检 —— 后者更隐蔽：运营看到「9 个商品通过」，实际是「9 个商品没被检查」。**两者都不可接受**。
2. 方案 C 满足章程 §5.2「明确哪些数据属于正式事实、风险线索、待核实记录」：缺失字段下的规则既不是事实也不是线索，而是**待核实**。
3. 「未评估」是运营能直接行动的信息（去补那个字段），而「通过」会让人停止追问。
4. `requires_input` 是**显式声明**，让规则作者承担「这条规则依赖哪些输入」的责任，避免隐式假设。

## 效果验证

修正后同一批数据的结论：

```
products reviewed : 15
products flagged  : 6      (2 阻断 + 4 待复核)
findings total    : 8
parse errors      : 3      ← 3 条规则未评估，各带原因
```

9 个商品真正通过，3 项检查明确标注未评估。**这才是可用的结论。**

## 风险与代价

- 规则作者可能忘记声明 `requires_input`，导致规则在缺字段时静默不评估 —— 缓解：引擎对每个带 `requires_input` 的规则做「全量输入中该字段是否存在」的检查，**整个批次都没有该字段时上报未评估**（已实现）。
- 结果中 `errors` 数量增加，可能被误读为「系统出错」—— 缓解：`severity: "warning"`，报告小节标题为「Erros de ingestão（nada foi descartado silenciosamente）」并区分「解析错误」与「未评估」。

## 回滚或替代条件

- **触发条件**：若某类输入（如 PDF）天然缺某字段，导致未评估项过多淹没报告。
- **替代方案**：按规则分类聚合未评估项（「以下 12 条规则因输入无图片字段而未评估」），而非逐条列出。
- **回滚**：移除 `requires_input` 语义会让规则回到方案 A/B 的危险状态 —— **不建议回滚**。
