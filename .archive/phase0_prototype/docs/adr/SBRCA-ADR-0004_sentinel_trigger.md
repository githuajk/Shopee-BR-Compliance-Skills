## 背景

重复刊登与重发判定**无法用文本模式表达** —— 它们需要跨记录比对（商品 A 与商品 B 的相似度、候选商品与历史案件的关联）。

而规则库必须是**可审阅、可 Schema 校验、可引文核验的数据**（章程 §2.3、§3.1、§5.3）。把相似度阈值写成 JSON 表达式既不可审阅也不可校验。

## 可选方案

| 方案 | 说明 |
|---|---|
| A | 规则 JSON 里直接写判定表达式（如 `similarity(other, this) > 0.72`） | 不可审阅、不可 Schema 校验、无法安全求值 |
| B | 引擎做全部判定，规则只声明「有重复」这一个粗粒度事实 | 规则层丢失严重度/证据/决策信息 |
| C | **哨兵触发**：引擎做判定并注入哨兵 token，规则层声明该结论的处置要求 |
| D | 判定完全在代码里，规则库不涉及重复/重发 | 处置要求无法被审阅，违背规则库作为权威源 |

## 评估标准

规则层可审阅性；Schema 可校验性；引文可核验性；复杂逻辑的可测试性；报告可读性。

## 最终选择

**方案 C（哨兵触发）**。

机制：
1. 引擎层（`duplicates.py` / `relist.py`）执行真实比对，把结论以哨兵 token 注入被检查字段：
   `__DUPLICATE_SIGNAL__` / `__CROSS_STORE_DUPLICATE_SIGNAL__` / `__RELIST_SIGNAL__` / `__OPEN_CASE_SIGNAL__` / `__REMOVED_LISTING_SIGNAL__`
2. 规则层用普通 `contains_any` 条件匹配哨兵，声明该结论的 `severity` / `decision` / `evidence_required` / `source_url`。
3. 引擎在产出发现时把哨兵命中**映射回真实证据描述**（双方 ID、匹配轴、相似度），报告中不出现裸 token。

## 选择理由

1. 处置要求（严重度、要什么证据、是否需人工）本质是**业务知识**，应留在可审阅的数据里 —— 方案 B/D 把它塞进代码，运营无法审阅。
2. 复杂判定（相似度计算、倒排索引、案件状态机）本质是**算法**，应留在代码里 —— 方案 A 把它塞进数据，评审者看不懂也无法测试。
3. 方案 C 让两者各自用合适的载体，且**规则层仍是 Schema 可校验 + 引文可核验的数据**（如 `SBR-DUP-002` 引用平台码 [302] 的原文）。
4. 哨兵 token 是**内部协议**，不是面向用户的概念；报告层已做映射。

## 风险与代价

- 多一层间接：理解引擎行为需同时看代码与规则。
- 哨兵若泄漏到报告会显得莫名其妙 —— 缓解：映射逻辑 + 「报告不出现裸 token」作为不变量测试。
- 哨兵是字符串，若真实商品文本恰好包含同名 token 会误触发 —— 缓解：token 使用双下划线包裹的保留前缀；Phase 2 需加断言（真实输入不含保留前缀）。

## 回滚或替代条件

- **触发条件**：若哨兵机制导致可读性或误触发问题频发。
- **替代方案**：改为「引擎直接产出 Finding，规则层用 `rule_id` 引用外部定义」—— 保留规则可审阅性但把映射改为显式注册表。
- **回滚**：仅影响 5 条规则与 `reviewer.py` 的映射段，不影响规则库其余部分。
