## 背景

章程 §1.2 要求区分「官方平台规则」与「内部风控建议」等 7 类来源，不得混为一谈。规则库是系统的权威判定依据 —— 若规则里的引文是编造的，整个判定链的合法性就塌了。

**这个风险不是假设，第一阶段实际发生了**：初版 `SBR-IP-006`（兼容性描述不算侵权）的 `source_excerpt` 写为：

> "Art. 125. Não constitui uso indevido o emprego da marca em rambling que se refira apenas ao tipo de produto…"

这段葡语**在 Planalto 的 Lei 9.279/1996 原文中根本不存在**。它是凭印象写出的"看起来合理"的条文。真实条文是 **Art. 132, II**，且 Planalto 的 HTML 渲染会丢失罗马数字（"I -" 变成 "-"），必须逐字匹配才能对上。

## 可选方案

| 方案 | 说明 |
|---|---|
| A | 信任人工，引文仅作参考 | 已实证失败 |
| B | 引文必填 + 人工评审 | 减少但不消除（评审者不可能逐条比对 10 万条） |
| C | 引文必填 + **自动逐字核验**（与抓取件比对） | 确定性保证 |
| D | 只存来源 URL，不存引文 | 无法离线核验；URL 会漂移/失效 |

## 评估标准

能否确定性地排除编造；可维护性；离线可用性；评审负担。

## 最终选择

**方案 C**，并与 D 互补：

1. 每条规则**必须**有 `source_url` + `source_excerpt` + `source_tier` + `last_verified`。
2. `tools/verify_citations.py` 把 `source_excerpt` 与 `research/raw/*.txt` 做**逐字比对**（仅归一化空白与句末标点，其余字符严格）。
3. 该检查**纳入测试套件**（不通过则测试失败）。
4. `source_url` 保留（人工追溯与未来重抓），但**核验依据是抓取件而非 URL** —— URL 会因平台改版漂移，抓取件是快照。
5. 规则变更流程中，"引文核验通过"是合并的前置条件。

## 选择理由

1. 编造引文是本项目**最严重的失败模式** —— 它会让一个基于虚构平台的判定被当作事实执行。自动核验是唯一能规模化防止它的手段。
2. 抓取件是快照，不受 URL 漂移影响；`last_verified` 记录快照日期，可判断新鲜度。
3. 归一化空白与句末标点是必要的：平台页面在规则文本中夹杂 UI 文案（"Para mais informações, clique aqui."），逐字匹配需容忍标点差异，但**不容忍措辞差异**。
4. 成本极低：当前 50 条规则核验耗时 < 1 秒。

## 风险与代价

- **严格性带来的维护摩擦**：改写规则描述时若连带改动引文，核验会失败（这是**特性**，不是缺陷）。
- 平台改版会使历史抓取件与线上不一致 —— 缓解：`last_verified` + 定期重抓；核验只保证「引文确实出自某次抓取」。
- 非连续引文不可拼接（2026-09 的教训：违规码 [325] 与 [342] 在原文中不相邻，拼接后无法逐字匹配）—— 缓解：只引连续的原文段，跨段引用写进 `description`。
- 归一化规则需明确：当前仅归一化空白与句末标点（`,` `.` `;` `:`），**不放宽措辞**。

## 回滚或替代条件

- **触发条件**：平台页面改版导致大量引文核验失败且重抓成本过高。
- **替代方案**：核验基准改为「规则文件内的引文与 `research/violation_codes.json` 等结构化派生数据比对」，仍保持逐字要求。
- **回滚**：不可回滚 —— 这是 §1.2 合规性的底线要求。
