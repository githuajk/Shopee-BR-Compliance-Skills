## 背景

章程 §8.2 **禁止**在架构阶段未经论证地锁定单一语言或框架。同时 §8.2 要求制定依赖管理规范。

当前实现状态：纯标准库（Python 3.14）。基础设施部分自研：

| 自研组件 | 行数量级 | 替代库 |
|---|---|---|
| XLSX 读取（zipfile + ElementTree） | ~120 | `openpyxl` |
| JSON Schema 校验器（draft 2020-12 子集） | ~250 | `jsonschema` |
| Aho-Corasick 自动机 | ~90 | `pyahocorasick` |
| CDP websocket 客户端 | ~140 | `websockets` |
| 测试 harness | ~470 | `pytest` |

环境约束：Hermes 运行时是 PEP 668 托管环境，`pip install` 不可保证；`openpyxl` 安装在第一阶段已实测失败。

## 可选方案

| 方案 | 说明 |
|---|---|
| A | 继续纯标准库，全部自研 |
| B | 全面引入第三方库（openpyxl + jsonschema + pytest + pyahocorasick） |
| C | 标准库为默认；**仅在有实测收益**时逐个引入并记 ADR |

## 评估标准

章程合规（不未经论证锁定）；运行环境可安装性；维护成本；交付形态（能否 clone 后直接跑）；长期可维护性；供应链风险。

## 最终选择

**方案 C**。

具体规则：
1. 默认纯标准库，项目必须能在无 pip 的环境 clone 后直接运行。
2. 任何新增依赖须有独立 ADR，论证须包含：替代方案、实测收益（性能/维护时间）、供应链风险、离线安装方案。
3. 依赖须固定版本并提供离线安装说明。

## 选择理由

1. 章程禁止**未经论证**地锁定，而非禁止依赖 —— 方案 C 恰好是"逐个论证"。
2. 方案 B 假设 pip 可用，但托管环境已实测不可用 —— 会让项目在目标环境无法运行。
3. 方案 A 忽略了自研基础设施的长期维护成本（Schema 校验器只实现子集，遇 `$dynamicRef` 等需扩展）。
4. 方案 C 保留零安装优势，同时允许在有实证收益时引入。

## 风险与代价

- 初期自研成本已付出（约 470 行基础设施）。
- 可能出现"某个库确实该引入但当时没引入"的反复 —— 缓解：ADR 流程本身允许随时补引入。
- `jsonschema` 库若引入，本项目自研校验器应保留为**开发期交叉验证工具**（两套实现结果必须一致）。

## 回滚或替代条件

- 若某依赖在目标环境无法离线安装 → 回退到自研实现。
- 若自研某组件的维护成本持续高于引入收益 → 走 ADR 引入并废弃自研版本。
