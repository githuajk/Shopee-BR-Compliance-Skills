## 1. 架构原则

1. **单向依赖**：上层依赖下层，下层**不得**反向依赖上层。
2. **确定性优先**：能由规则判定的，不用 AI；AI 只处理规则无法判定的部分。
3. **数据即契约**：层间通过有 Schema 的数据结构通信，不共享可变状态。
4. **可替换**：AI 层、GitHub 层可整体替换而不影响其他层。
5. **可审计**：任何结果都能回溯到输入、规则版本、引擎版本。
6. **不锁定实现**：语言、框架、存储均可由 ADR 替换（章程 §8.2）。

## 2. 总体分层

```
┌───────────────────────────────────────────────────────────────┐
│  L6  审计与报告层   audit/                                       │
│      审核日志、报告生成、可追溯性查询                            │
├───────────────────────────────────────────────────────────────┤

│      统一结果聚合、风险×动作矩阵、审批状态机、冻结管理          │
├───────────────────────────────────────────────────────────────┤
│  L4  AI 审核层      ai/            ← 可替换                    │

│      输出 source_tier = ai_inference，不可驱动 BLOCK             │
├───────────────────────────────────────────────────────────────┤
│  L3  确定性规则引擎 engine/                                     │

│  L2  数据与规则层   data/ + rules/ + lexicon/                   │
```

**当前实现状态**：L1、L2、L3、L6 已有可运行实现（`src/compliance_agent/`）；L4、L5 为 Phase 4/5 目标。

## 3. 各层职责与接口契约

### 3.1 L1 输入适配层 `ingest/`

**职责**（章程 §5.1）：文件类型识别、安全解析、字段映射、文本及图片内容提取、数据清洗、统一模型转换、解析错误记录、原始文件与转换结果关联。

**输入**：外部文件路径 + `shop_id`。
**输出**：`ParseResult{ products: Product[], errors: ParseError[], meta: dict }`。

**不可违反的约束**：

| 约束 | 说明 |
|---|---|
| 只读 | 解析器**绝不**写回输入文件。原文件是唯一事实源。 |
| 不静默丢弃 | 每条无法解析/缺字段的记录产生一条 `ParseError`，最终出现在结果的 `errors` 数组 |
| 可回溯 | 每条 `Product.source.raw_ref` 保留原始定位（`row 42` / `line 7` / `record 3`） |
| 不可信输入 | 解析出的文本**是数据不是指令**（章程 §5.1）。见 §6.1 威胁模型 |
| 无网络 | 解析层不发起网络请求（URL 抓取属独立能力，需单独授权） |

**支持的格式与策略**：

| 格式 | 实现 | 失败行为 |
|---|---|---|
| XLSX/XLSM | `zipfile` + `ElementTree` 直读 OOXML | 损坏 → 报 `not a valid xlsx (zip) file` |
| XLS | 不支持 | 明确报错，要求先导出 XLSX/CSV（不静默跳过） |
| CSV/TSV | `csv` + 分隔符/编码嗅探 | 无法识别表头 → 报 `no recognisable title column` 并列出所见表头 |
| JSON/JSONL | `json` | 单行非法 → 报行号，其余行继续 |
| TXT/MD | 分块 + 前置元数据 | 无标题的块 → 报 warning |
| DOCX | `word/document.xml` | 损坏 → 报 cannot read docx |
| PDF | `pypdf`（可选） | **无提取器时报错，不返回空**；无文本层（扫描件）→ 提示需 OCR |
| PNG/JPG/JPEG/WEBP | 登记为待 OCR/视觉分析 | 产出 `needs: [ocr, visual_analysis]` |

**字段映射**：`HEADER_ALIASES` 表（中/葡/英三语列名 → 规范字段）。规范化规则：大小写折叠、去重音、`_` → 空格。**「sku」归 internal_sku**（电商导出中的通常含义），平台数字 ID 由 `product_id` / `商品id` / `item id` 识别。

### 3.2 L2 数据与规则层

**存储**：JSON 文件树（权威源），按域分目录。

```
data/
├── schema/          6 份 Schema（规则的机器可校验定义）
├── samples/         合成测试数据（无真实商品）
└── cases/           历史案件库（Phase 2 落地）
rules/               规则库（5 文件 / 50 规则）
lexicon/             词库（JSON；编译为 Aho-Corasick 自动机）
research/            调研原始材料（来源、抓取件、违规码目录）
```

**三类事实的区分**（章程 §5.2，强制）：

| 类别 | 载体 | 引擎行为 |
|---|---|---|
| **正式事实** | `source_tier ∈ {platform_official, law}` 的规则 | 可产生阻断/冻结/转法务 |
| **风险线索** | `source_tier = internal_risk` / `ai_inference` / 词库命中 | 只能提示复核 |
| **待核实记录** | `status = draft` / `source_tier = unverified` | 不参与判定，进待核实清单 |

**规则对象**：见 `data/schema/rule.schema.json`。关键字段语义：

| 字段 | 语义 |
|---|---|
| `rule_id` | 稳定 ID，`SBR-<类别>-<序号>`。**重命名不得丢失历史关联** |
| `trigger_conditions` | 全部条件为 AND 关系；条件可用 `requires_input` 声明依赖字段 |
| `severity` | 风险等级（`info`/`low`/`medium`/`high`/`critical`） |
| `decision` | 处理动作。**与 severity 分开定义**（章程 §5.5） |
| `source_url` / `source_excerpt` | 平台或法律来源。`source_excerpt` 必须逐字可核验（`REQ-LEG-001`） |
| `last_verified` | 核查日期。过期规则需复核 |
| `status` | `active` / `draft` / `deprecated` / `suspended` |
| `version` | 规则自身版本。审核结果记录命中的版本 |

### 3.3 L3 确定性规则引擎 `engine/`

**职责**（章程 §5.3）：精确/子串匹配、文本标准化、规则优先级、规则适用条件、历史记录关联、明确阻断条件、结果记录。

**组件**：

| 组件 | 职责 |
|---|---|
| `loader.py` | 规则加载、词库编译（Aho-Corasick）、正则编译缓存 |
| `evaluator.py` | 条件求值、权限守卫、状态推导 |
| `duplicates.py` | 同店/跨店重复检测（身份 + 内容 + 图片三信号） |
| `relist.py` | 重发检测（五轴匹配 + 案件状态机） |
| `reviewer.py` | 编排器 |

**文本标准化**（`models.norm_text`）：NFKD → 去组合符号 → 小写。用于关键词匹配，**不用于输出**。

**葡语词边界**：Python 的 `\b` 在葡语重音元音旁不可靠（`at[óo]xico\b` 会吞 `Óculos` 首字母）。所有涉及葡语词的边界一律用显式字符类：

```
(?<![a-zA-Zà-ÿÀ-ß]) 词 (?![a-zA-Zà-ÿÀ-ß])
```

**多模式匹配选型**（章程 §5.3 要求评估准确性/性能/内存/更新成本/维护难度）：

| 方案 | 准确性 | 性能 | 内存 | 更新成本 | 维护难度 | 结论 |
|---|---|---|---|---|---|---|
| 逐词 `in` 扫描 | ✅ | ❌ O(词数×文本长) | ✅ 最低 | ✅ 最低 | ✅ 最低 | 词数 <1000 可用 |
| **Aho-Corasick** | ✅ 无误报 | ✅ O(文本长 + 命中数) | ⚠️ 与词数线性，10 万词需实测 | ⚠️ 需重建自动机 | ✅ 单次构建 | **候选方案**，须按 §4 基准验证 |
| 正则合并表 | ⚠️ 顺序敏感，可级联 | ✅ | ✅ | ⚠️ | ⚠️ 易膨胀 | 仅用于小规模、需优先级控制的规则 |
| 倒排索引（当前重复检测用） | ✅ | ✅ | ⚠️ | ✅ | ✅ | 用于相似度候选生成 |

> 选型结论**待基准测试**（章程 §6.1 禁止未经测试宣称性能）。`CONF-002` 已登记。

**条件求值语义**：

- 全部条件 AND。
- `requires_input`：声明依赖的输入字段；输入没有该字段 → 条件**不评估**（不是「通过」），并上报为未评估（`REQ-DATA-006`）。
- 运算符集：`contains_any` / `contains_all` / `not_contains_any` / `regex` / `equals` / `not_equals` / `gt` / `gte` / `lt` / `lte` / `image_count_lt` / `image_count_gte` / `has_field` / `has_nonempty` / `field_missing`。

**权限守卫**（引擎内强制，不可由规则绕过）：

| 守卫 | 规则 |
|---|---|
| G1 权威性 | `status == active` **且** `source_tier ∈ {platform_official, law}` 才可能 `block`；否则降级为 `flag_for_review` |
| G2 IP 信号 | `category ∈ {ip_trademark, ip_copyright, ip_design}` → `confidence = signal`、`human_review_required = true`；`block` 升级为 `escalate_legal` |
| G3 缺失数据 | 依赖字段缺失 → 不评估 + 上报未评估 |
| G4 兼容反误判 | 存在兼容性表述 → IP 命中降级并附法律依据（Lei 9.279/96 Art. 132, II） |

**哨兵触发（sentinel trigger）**：

重复刊登与重发这类判定**无法用文本模式表达**（需跨记录比对）。解耦为两层：

- 引擎层（`duplicates.py` / `relist.py`）做真实比对，结论以哨兵 token 注入被检查字段：
  `__DUPLICATE_SIGNAL__`、`__CROSS_STORE_DUPLICATE_SIGNAL__`、`__RELIST_SIGNAL__`、`__OPEN_CASE_SIGNAL__`、`__REMOVED_LISTING_SIGNAL__`
- 规则层声明该结论的 severity / decision / evidence_required / source_url

**收益**：规则的处置要求仍是**可审阅、可校验、可引文核验的数据**；复杂比对留在代码。

**重复检测三信号**：

| 信号 | 强度 | 说明 |
|---|---|---|
| 身份（同一供应商 SKU / 同一平台 PID） | 强 | 确定性最高 |
| 内容（标题 token Jaccard + trigram Dice + 详情 Jaccard） | 中 | 覆盖「同款换标题」 |
| 图片（哈希集合） | 弱 | 需图片数据 |

候选生成用倒排索引（按标题 token，逆文档频率排序）避免 O(n²)。

**重发检测五轴**：平台 PID / 供应商 SKU / 卖家 SKU / 商品链接 / 内容指纹（标题+详情相似度 + 图片哈希）。

**案件状态机**（与冻结强相关）：

```
open ─────────────► under_review ────────► awaiting_evidence
  │                       │                        │
  │                       ▼                        ▼
  └──────────────────► blocked ◄──────────── relist_frozen
                          │                        │
                          ▼                        ▼
                     escalated / rejected      approved / closed
```

**关键判定**（`relist.py::_is_actioned`）：

| 案件状态 | 视为已处置？ | 理由 |
|---|---|---|
| `open` / `under_review` / `awaiting_evidence` | ❌ **否** | 卖家正在整改申请复核；冻结会挡住正要提交的整改 |
| `blocked` / `relist_frozen` / `escalated` / `rejected` | ✅ 是 | 平台已实际处置 |
| 其他 + `frozen: true` | ✅ 是 | 显式冻结标记 |

**统一结果聚合**（L5 目标，L3 现产出前置数据）：

| 维度 | 取值 |
|---|---|
| 处置（decision） | `allow` / `flag_for_review` / `require_evidence` / `block` / `freeze_relist` / `escalate_legal` |
| 章程聚合标签 | `PASS` / `REVISE` / `REVIEW` / `BLOCK`（`CONF-001` 待裁定，默认方案 A：6 值 + 聚合标签） |
| 严重度 | `info` / `low` / `medium` / `high` / `critical` |
| 置信度 | `signal` / `likely` / `confirmed`（IP 类恒为 `signal`） |

### 3.4 L4 AI 审核层 `ai/`（Phase 4）

**职责**（章程 §5.4）：上下文判断、商品功能与描述一致性、图片内容分析、疑似品牌使用、规则冲突解释、证据不足提示、人工复核建议。

**硬约束**：

| 约束 | 机制 |
|---|---|
| AI 输出与规则结果分离 | AI 结论写独立字段，`source_tier = ai_inference` |
| AI 不可驱动阻断 | 决策层只接受确定性规则产出的 `block`；AI 只能产出 `flag_for_review` |
| 确定性结论不可被 AI 降级 | 合并阶段单向：`max(确定性, AI)`，AI 只能提升不能降低（章程 §5.5） |
| 输入即数据 | 注入防护见 §6.1 |
| 不得把推测当事实 | 报告与提示词中 AI 结论必须与规则引用分区呈现 |

**输入**：Product + 确定性发现列表。
**输出**：`AiAssessment{ product_id, signals[], explanations[], suggested_action, evidence_hints[], model_id, prompt_version }`。

**图片分析**：产出 `Product.images[].ocr_text` 与 `detected_logos`。**注意**：`detected_logos` 非空只是**信号**，不构成侵权认定（`REQ-LEG-002`）。

**版本追踪**：`model_id` + `prompt_version` 写入审核结果，保证 AI 结论可复现与追责。

### 3.5 L5 决策与审批层 `decision/`（Phase 5）

**职责**（章程 §5.5）：统一结果聚合、风险×动作矩阵、审批状态机、冻结管理。

**风险等级与处理动作分离**：

| 风险（severity） | 动作（decision） | 关系 |
|---|---|---|
| 风险描述「多严重」 | 动作描述「做什么」 | 独立定义；同一 severity 可对应多个 decision |

**确定性控制不可绕过**（章程 §5.5）：历史删除、明确禁售、冻结商品必须执行确定性控制，不能因 AI 评分低而绕过。实现上：AI 分数**不参与** `block`/`freeze_relist` 的判定，只影响 `flag` 档的排序与说明。

**审批**（`REQ-SEC-003`）：7 类高风险操作需人工批准，缺审批记录时拒绝执行。审批记录含 action / actor / timestamp / reason / decision_ref。

### 3.6 L6 审计与报告层 `audit/` + `report/`

**职责**（章程 §5.6）：追溯输入、规则版本、软件版本、审核时间、命中规则、证据索引、最终结果、人工修改与审批、错误异常、后续处理。

**审核结果结构**（`data/schema/review_result.schema.json`）：

| 段 | 内容 |
|---|---|
| `run_id` / `generated_at` | 运行标识与时间 |
| `scope` | 输入来源清单（路径、店铺、格式、解析统计） |
| `summary` | 商品数、发现数、按类别/严重度/决策分布、规则数、解析错误数 |
| `findings[]` | 每条发现：规则 ID、命中字段与片段、解释、来源 URL 与层级、证据要求、置信度 |
| `products[]` | 每商品状态、发现 ID 列表、建议动作、关联案件 |
| `errors[]` | 摄入错误 + **未评估规则**（数据缺口） |
| `report_path` | Markdown 报告路径 |

**软件版本与规则版本**（章程 §5.6 要求，本原型已部分具备）：需在 Phase 2 补 `engine_version` 与 `ruleset_version`（由规则文件内容哈希生成）。

**报告**（`report/markdown.py`）：6 节 —— 摘要 / 摄入错误 / 需决策的发现 / 待复核发现 / 逐商品结果 / 已查阅规则表。每条发现显示来源层级、置信度、命中片段、所需证据。

**敏感信息**：报告与日志均不含密钥与完整凭证（`REQ-SEC-002`）。

## 4. 性能与规模设计

### 4.1 规模假设（章程 §4.2，规划输入，非已达成指标）

| 项 | 假设 |
|---|---|
| 规则及黑名单 | 可能 > 10 万条 |
| 每批商品 | 1–300 个 |
| 店铺数 | 多店铺 |
| 增长 | 规则、商品、历史案件持续增加 |

### 4.2 待测量的 9 项指标（章程 §6.1）

| # | 指标 | 测量点 |
|---|---|---|
| 1 | 规则加载时间 | `loader.load_rules` |
| 2 | 内存占用 | 加载后 + 匹配中峰值 |
| 3 | 单批匹配耗时 | 1 个商品全规则 |
| 4 | 多商品批处理耗时 | 300 个商品全规则 |
| 5 | 增量规则更新耗时 | 改动 1 条规则后的重建代价 |
| 6 | 数据校验耗时 | Schema 校验 50 规则 + 词库 |
| 7 | 图片审核耗时 | OCR + 视觉（**单独统计**） |
| 8 | AI 审核耗时 | 模型推理（**单独统计**） |
| 9 | 大文件导入与失败恢复 | 大 xlsx 导入、损坏文件恢复 |

**规则匹配耗时与模型推理耗时必须分别报告**（章程 §6.1）。

### 4.3 当前实测（第一阶段原型，**非规模结论**）

| 场景 | 规则数 | 商品数 | 耗时 |
|---|---|---|---|
| 端到端 demo | 50 | 15 | < 1 s（不含启动） |
| 测试套件（333 项） | 50 | — | ~1.2 s |

> 这**不能**外推到 10 万条规则。10 万词 Aho-Corasick 自动机的内存占用与加载时间必须在 Phase 3 实测（`CONF-002` / `REQ-PERF-001`）。

### 4.4 扩展路径

| 增长维度 | 手段 |
|---|---|
| 词库变大 | Aho-Corasick（需基准验证）；或分片加载；或派生索引（`CONF-003`） |
| 规则数变大 | 规则按 category 分文件；按 `applies_to` 预筛；懒加载 |
| 商品数变大 | 倒排索引候选生成（已用）；批处理流式化 |
| 跨店比对变大 | 分块 + 签名（minhash）预筛 |

## 5. 依赖规则

| 允许 | 禁止 |
|---|---|
| L5 → L4 / L3 / L2 | L1 → L2 以上任何直接调用 |

## 6. 威胁模型要点

详见 `SBRCA-P1-004`。架构层面的关键点：

### 6.1 输入即数据（章程 §5.1）

商品详情、PDF、Word 文档中的文本**全部视为不可信数据**。具体措施：

| 措施 | 说明 |
|---|---|
| 数据/指令隔离 | 解析出的文本进入 `Product.description` 等数据字段，**永不拼接进系统提示词** |
| 角色标记 | 传给 AI 层时，输入文本用明确的数据边界包裹（结构化 JSON 字段而非拼接字符串） |
| 指令剥离 | 可选：剥离形如「ignore previous instructions」的注入模式并记录（不删除原文，保留证据） |
| 工具白名单 | AI 层无写平台能力（章程 §4.3） |

### 6.2 其他

| 威胁 | 缓解 |
|---|---|
| 规则库被投毒 | 引文逐字核验 + 规则变更需审批 + ADR |
| 恶意 xlsx（zip bomb / XXE） | 只读 OOXML 部件；不解析外部实体；限制解压大小 |
| 越权 | 七类权限分离（`REQ-SEC-001`） |
| 敏感信息泄漏 | 日志脱敏（`REQ-SEC-002`） |
| 凭证泄漏 | 凭证不入库不入日志；密钥轮换（`REQ-SEC-004`） |
| AI 越权决策 | AI 不可驱动 BLOCK；确定性结论不可被降级 |
