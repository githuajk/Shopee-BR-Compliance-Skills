## 1. 目的与定位

SBRCA（Shopee Brazil Compliance Agent）是面向巴西 Shopee 运营的**商品合规审核系统**。

它被建设为**长期维护、模块化、可测试、可审计的业务软件系统**，而不是一次性脚本、提示词、静态违禁词表或临时自动化工具。

### 1.1 系统能力边界（目标态）

| 能力域 | 说明 |
|---|---|
| 商品内容审核 | 标题、详情、属性、图片、视频的风险识别 |
| 禁限售检查 | 禁售类目、受限类目、授权要求 |
| 检索 | 大规模关键词与规则库检索 |
| 关联分析 | 重复刊登、跨店铺同款关联 |
| 历史追踪 | 已删除/暂停/被投诉商品的历史记录查询 |
| IP 风险 | 商标、版权、外观设计、专利、授权筛查 |
| 数据接入 | Excel / PDF / Word / 图片 / 结构化数据 / 商品链接 |
| 统一模型 | 统一数据模型与结构化审核结果 |
| 人机协同 | AI Agent 与确定性规则引擎协同 |
| 治理 | 人工审批、证据留存、规则版本管理、审计 |
| 集成 | GitHub 受控分支 / Commit / PR 工作流 |

### 1.2 优先级原则

**正确性 > 安全性 > 可维护性 > 可追溯性 > 开发速度 > 功能数量。**

当出现冲突时按此顺序裁决。若两个同等优先级项冲突，升级至用户裁定（不得由实现者自行决定）。

### 1.3 非目标（明确排除）

以下内容**不属于**本项目范围，不得在未获单独批准前实施：

- 自动发布商品 / 自动修改线上商品 / 自动删除或下架商品
- 自动解除冻结 / 自动发送正式申诉 / 自动接受或拒绝 IP 投诉
- 未经审核直接合并到 GitHub 主分支
- 将用户资料发送至未经批准的第三方服务
- 硬编码为单一品类（汽车用品 / RotaPeca 是背景之一，非限制）

## 2. 角色与职责

| 角色 | 职责 | 不得做 |
|---|---|---|
| **用户 / 业务负责人** | 业务规则最终批准人；裁定冲突与待确认事项；批准高风险操作 | — |
| **技术负责人 / 架构师**（本 Agent 角色） | 架构设计、技术选型论证、实现、文档、测试执行；登记 ADR 与变更 | 不得自行批准业务规则；不得把未确认的建议表述为已定方案 |
| **规则维护者** | 维护规则库、来源引文、核查日期、版本 | 不得在无来源情况下新增阻断级规则 |
| **审核员** | 使用审核结果做人工判断、录入审批记录 | 不得跳过证据要求 |
| **审批人** | 批准高风险操作 | — |

### 2.1 信息源分层（强制）

任何文档、规则、结论必须标明其来源层级，**不得混同**：

| tier | 含义 | 处置权限 |
|---|---|---|
| `platform_official` | Shopee 官方页面明确写出 | 可作为处置依据 |
| `law` | 巴西联邦法律明文规定 | 可作为处置依据 |
| `internal_risk` | 内部风控建议、运营经验 | **仅提示复核，不可阻断** |
| `unverified` | 未验证假设 | **仅进入待核实清单** |
| `ai_inference` | AI 模型推断 | **不可驱动阻断，不可表述为官方事实** |
| `technical` | 技术调研与实测结论 | 不可作为业务规则依据 |
| `confirmed` | 用户已明确确认的需求 | 可作为需求依据 |

### 2.2 冲突处理流程

发现冲突 → 登记到 `SBRCA-P0-004` → 分析影响与选项 → 给出建议与默认处置 → **提交用户裁定** → 裁定结果写入 ADR → 更新受影响文档。

**不得**擅自覆盖已确认的要求。

## 3. 文件与数据治理

### 3.1 格式政策

| 用途 | 唯一允许格式 |
|---|---|
| 结构化数据、规则、配置、审核记录、测试数据、Schema、接口数据、结构化报告 | **JSON** |
| SOP、需求规格、调研报告、架构设计、操作手册、Agent 提示词、变更说明 | **Markdown** |

**禁止**作为内部正式数据源：YAML、JSONL、CSV、TXT、XML。

**不适用**：程序源代码（`.py` 等）、二进制测试素材（xlsx、jpg 等）、外部输入文件。

外部输入（XLSX/XLS/CSV/JSONL/TXT/MD/PDF/DOCX/图片/链接）**必须**经输入适配层转换为统一模型后，以 JSON 或 Markdown 落盘。

Excel 仅作输入与人工编辑来源，**不得**作为规则库的唯一存储。

### 3.2 JSON 规范

UTF-8；统一字段命名（见 `SBRCA-P1-003`）；明确类型；必要字段完整；唯一 ID 不重复；引用关系有效；日期 ISO 8601；无注释、无尾随逗号、无非标准语法；**不得**用不可解释的自由字段代替结构化定义；**缺失 / 未知 / 不适用 / 待核实**四种状态必须显式区分（见 `SBRCA-P1-003` §4）；敏感字段不得因调试输出到普通日志。

核心 JSON 结构必须有对应 Schema 或等效的机器可校验定义。

### 3.3 Markdown 规范

每份文档必须含：标题、文档 ID 或稳定路径、版本号、状态（Draft / Review / Approved / Deprecated）、创建或最近更新时间、适用范围、正文、相关文档链接、尚未确定事项。

**不得**将未经核实的内容表述为正式制度。

### 3.4 命名规范

- 英文小写；词间用下划线；扩展名 `.json` / `.md`。
- 治理文档：`SBRCA-P<phase>-<seq>_<snake_case_name>.<ext>`（例：`SBRCA-P1-002_architecture.md`）。
- 数据文件：`<domain>_<subject>.json`（例：`rules/01_prohibited_restricted_items.json`）。
- **不以文件名日期代替版本管理**；版本写在文档元信息与 Schema 内。
- 核心数据以稳定 ID 引用（`rule_id` / `product_id` / `case_id` / `requirement_id`）。
- **规则重命名不得导致历史记录失去关联** —— 重命名须在 ADR 登记并提供 ID 映射。

### 3.5 版本管理

正式规则、数据 Schema、接口、核心流程必须有明确版本。变更流程：

```
需求确认 → 影响分析 → 实施 → 测试 → 代码审查 → 发布 → 记录
```

破坏兼容性的变更必须先提供迁移方案（受影响文件清单、转换方式、回滚步骤）。

## 4. 工程规范

### 4.1 编码风格

| 项 | 约定 |
|---|---|
| 语言 | Python 3.11+（当前运行时 3.14）；**不锁定**，见 ADR-0002 |
| 行宽 | 100 |
| 命名 | 模块/函数 `snake_case`；类 `PascalCase`；常量 `UPPER_SNAKE`；私有前缀 `_` |
| 类型注解 | 公共函数必须有类型注解 |
| 文档字符串 | 公共模块、类、函数必须有 docstring，说明**为什么**而非复述代码 |
| import | 标准库 → 第三方 → 本地，三段之间空行；禁止 `from x import *` |

### 4.2 类型约束

- 核心数据模型使用 `dataclass` + 显式类型；JSON 边界用 Schema 校验后再构造。
- 可空性显式声明（`str | None`），**禁止**用空字符串表达「无值」（见 §3.2 四态）。
- 枚举值集中定义，不散落字面量。

### 4.3 错误处理

- 解析层错误**必须**结构化记录并继续处理其余数据，**禁止**静默丢弃。
- 引擎层错误**必须**抛出（快速失败），**禁止**用默认值掩盖规则错误。
- 错误信息须含：阶段、来源、消息、上下文。
- 禁止裸 `except:`；禁止 `except Exception: pass`。

### 4.4 日志规范

- 级别：`DEBUG`（开发）/ `INFO`（运行摘要）/ `WARNING`（未评估、数据缺口）/ `ERROR`（失败）。
- 每条日志含：时间、级别、阶段、来源、可定位标识（run_id / product_id / rule_id）。
- **禁止**记录：API 密钥、令牌、完整授权凭证、完整身份证/银行卡号、用户密码。
- 敏感字段需脱敏后再输出（见 `SBRCA-P1-004` §5）。

### 4.5 接口规范

- 层间通过**数据结构**通信，不通过共享可变状态。
- 每个公共函数有明确输入输出类型与错误语义。
- 跨层调用必须校验（Schema 或类型断言），不信任上游。

### 4.6 依赖管理

见 `SBRCA-P0-004` CONF-004（待裁定）。当前默认：**零第三方依赖**（纯标准库），每个新增依赖须有 ADR 论证。

### 4.7 测试覆盖要求

| 层 | 要求 |
|---|---|
| 单元测试 | 所有公共函数与规则分支 |
| Schema 测试 | 所有核心 JSON 结构 |
| 引擎测试 | 每条规则至少一个触发用例 + 一个不触发用例 |
| 解析测试 | 每种声明支持的格式 + 各自的失败路径 |
| 集成测试 | 端到端审核流程 |
| 回归测试 | 固定夹具集，跨版本对比结果差异 |
| 权限安全测试 | 越权拒绝、敏感信息不落日志、注入防护 |
| 性能基准 | 见 `SBRCA-P1-005` §4 |
| 端到端 | 从输入文件到报告产出的完整链路 |

**没有真实执行的测试不得标记为通过**（章程 §6.3）。

### 4.8 代码审查规则

- 至少 1 名非作者评审。
- 必查项：来源层级是否正确标注、引文是否逐字可核验、是否引入未确认的行为变更、缺失语义是否被混用、是否有裸 except、是否有敏感信息输出。
- 规则库变更必须附引文核验结果。

### 4.9 安全检查规则

见 `SBRCA-P1-004`。

## 5. 权限与高风险操作

### 5.1 最小权限

七类权限相互独立；**普通审核 Agent 默认只持有只读查询与结果生成权**。

| 权限 | 典型动作 | 默认持有者 |
|---|---|---|
| `read` | 查询商品、规则、案件、历史 | 审核 Agent |
| `ingest` | 导入文件、写入规范化 JSON | 审核 Agent（写入受限目录） |
| `rule_edit` | 新增/修改规则、词库 | 规则维护者 |
| `case_handle` | 创建/推进案件、标记冻结 | 审核员 |
| `approve` | 审批、解除冻结、结案 | 审批人 |
| `gh_write` | 创建分支/Commit/PR | 集成模块（受限于仓库与路径白名单） |
| `release` | 合并主分支、发布规则版本 | 审批人 |

### 5.2 高风险操作（默认需人工批准）

1. 解除违规冻结
2. 处理重大 IP 投诉
3. 修改核心规则
4. 直接修改生产数据
5. 变更权限配置
6. 合并到受保护主分支
7. 删除或覆盖重要历史记录

### 5.3 GitHub 安全边界

- 合法授权凭证，存放于受保护服务端环境或密钥管理系统，**不落仓库**。
- 仓库范围限制、分支限制、文件路径白名单、Commit 记录、PR 审核、密钥轮换、审计日志、失败重试与幂等、回滚机制 —— 10 项机制须在 Phase 6 逐项落实。
- **减少网页登录操作 ≠ 允许匿名写入或绕过授权。**

## 6. 审计要求

每次审核必须可追溯：使用的输入、规则版本、软件版本、审核时间、命中规则、原始证据索引、最终结果、人工修改及审批、错误与异常、后续处理结果。

日志不得无必要保存密钥、完整授权凭证或其他敏感信息。

## 8. 完成定义（DoD）

单个开发任务完成**至少**满足：

1. 实际修改了预期文件（逐项对照）
2. 格式校验通过
3. 相关测试**实际执行并记录结果**
4. 无已知未处理的重大错误
5. 文档与实现一致
6. 安全影响已检查
7. 变更范围与回滚方式明确

**不能因为代码已经生成就认定任务完成。**
