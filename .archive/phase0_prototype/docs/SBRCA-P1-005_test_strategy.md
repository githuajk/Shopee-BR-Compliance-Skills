## 1. 原则

| 原则 | 说明 |
|---|---|
| **真实性** | 没有真实执行的测试不得标记为通过（章程 §6.3、§8.4）。文档中的通过结论必须附执行日期与输出 |
| **可复现** | 测试用固定夹具；随机成分必须固定种子 |
| **分层** | 越下层越快越细；越上层越慢越接近真实 |
| **误报优先监控** | 误封正常商品的代价 > 漏掉一个风险商品的代价（见 §6） |
| **边界显式** | 缺失数据不是「通过」；未评估必须可见 |

### 3.2 规则级测试要求

每条规则**至少**两个用例：

| 用例 | 断言 |
|---|---|
| 正例 | 命中该规则，且 `decision` 与 `severity` 符合规则声明 |
| 反例 | **不**命中该规则（防止规则过度宽泛） |

**反例的来源**：从 `data/samples/` 的正常商品池中取；若无合适反例，说明该规则可能过宽，需复核。

> 第一阶段 50 条规则中，只有部分有独立正/反例。Phase 3 需补齐到 100%。

## 5. 误报与漏报监控

### 5.1 定义

| 指标 | 定义 |
|---|---|
| **误报率 (FPR)** | 被判违规/复核但实际合规的商品数 ÷ 实际合规商品数 |
| **漏报率 (FNR)** | 实际违规但未被判违规/复核的商品数 ÷ 实际违规商品数 |
| **误封率** | 被 `block` 但实际合规的商品数 ÷ 实际合规商品数（**最高优先级**） |
| **复核负担** | 需人工复核的商品数 ÷ 总商品数（影响运营成本） |

### 5.2 标注来源

| 来源 | 说明 |
|---|---|
| 运营复核结果 | 审核员对每条发现的判定（合规/违规/存疑）→ 写入审批记录 |
| 平台实际处置 | 平台是否真的下架/扣分（滞后但最权威） |
| 历史案例 | 2026-09 店主 491 条审阅结论（可作基准集） |

### 5.3 人工纠正闭环

```
AI/引擎结论 → 人工判定 → 审批记录（actor/时间/理由） → 汇总为误报/漏报统计
                                              ↓
                                    规则修订（需 ADR + 引文核验）
```

`REQ-QUAL-002` 要求人工纠正可回放 → 审批记录须保留纠正前后的结论。

### 5.4 已知的高误报来源（来自历史经验）

| 来源 | 现象 | 处置 |
|---|---|---|
| 店主 2026-09 审阅 | 491 个详情完全相同（模板化） | 跨商品详情相似度检测 → 独立规则 |
| chongyang1 | 57 处触线命中全为误报（`reduzir` 46 / `desconforto` 4 / `seguro` 1） | 关键词命中必须带**上下文判定** |
| zzj-02 | 兼容性描述被误判侵权 | `SBR-IP-006` 反误判规则 |
| 演示首版 | 15/15 全被判违规（输入缺列） | `requires_input` + 未评估上报 |

> **这四条是本项目最有价值的历史教训**，已固化为不变量与规则。

## 6. 测试夹具规划

### 6.1 目录

```
data/samples/
├── test_cases.json          8 个场景用例（合成）
├── demo_mass_update.xlsx    合成 Shopee 导出（15 行）
└── (Phase 2+)
    ├── normal_pool.json      正常商品池（用作规则反例）
    ├── edge_cases.json       边界与资料缺失
    └── conflict_cases.json   规则冲突
```

**全部为合成数据**，不含真实商品。真实历史案例按 `Q-H` 决定路径后单独存放于 `data/cases/`（不进公开仓库）。

### 6.2 夹具构造原则

| 原则 | 说明 |
|---|---|
| 合成优先 | 不复制真实商品到项目目录（章程 §2.1 数据安全） |
| 覆盖真实形态 | 夹具应模拟真实 xlsx 的 6 行 banner + 表头结构 |
| 正反成对 | 每个违规样本配一个"看起来像但合规"的对照 |
| 可归因 | 每个夹具说明它针对哪条规则、期望什么结论 |
