## 1. 六节固定结构

```
## 1. 摘要
## 2. 数据缺口与未评估项
## 3. 需决策的发现
## 4. 待复核的发现
## 5. 逐商品结果
## 6. 已查阅规则
## 硬约束
```

**顺序固定，不得调整。** 机器消费方依赖这个结构。

末尾的「硬约束」节是第 7 节 —— 它是必选的，列出本次执行的 H1–H6 自检行。

## 2. 各节内容

| 节 | 内容 | 空时的表现 |
|---|---|---|
| 1. 摘要 | 范围、商品数、结论分布、发现数、未评估数 | 必须有 |
| 2. 数据缺口 | 所有 `unevaluated[]` 条目、待补齐证据、被契约拒绝的结果、跨模块冲突 | **必须显示"无"**，不得省略 |
| 3. 需决策的发现 | `action` 为 `block` / `revise` / `freeze_relist` / `escalate_legal` 的 | 显示"无" |
| 4. 待复核的发现 | `action` 为 `flag_for_review` / `require_evidence` 的 | 显示"无" |
| 5. 逐商品结果 | 每个商品一条，含所有结论 | 必须有 |
| 6. 已查阅规则 | 本次用到的规则及其来源层级与核查日期 | 必须有 |
| 硬约束 | H1–H6 的执行自检 | 必须有 |

> ⚠️ **第 2 节是硬性要求。** 它把"未评估"与"通过"明确分区。
> 省略第 2 节会让读者误以为没问题的商品是通过了审核。

## 3. 第 1 节「摘要」的指标

摘要必须让读者在 30 秒内判断「要不要现在处理这批货」。因此它固定包含：

| 指标 | 来源 |
|---|---|
| 审核目标数 | `summary.target_count` |
| 输入结果条数 | `summary.input_result_count` |
| 整批结论 / 动作 / 风险等级 | 整批 `AuditResult` 的三个字段 |
| 需人工处理的目标数 | `summary.needs_human_review_count` |
| 结论分布表 | `summary.verdict_counts`（PASS/REVISE/REVIEW/BLOCK 四行**全部列出**，含 0） |
| 命中规则数（去重后） | `summary.rule_count` |
| 需补齐证据数 | `summary.missing_evidence_count` |
| 未评估条目数 | `summary.unevaluated_count` |
| 错误记录数 | `summary.error_count` |

**结论分布表的四行必须全部出现**，即使某档为 0 —— 否则读者无法区分
「没有 REVIEW 的商品」和「REVIEW 这一栏忘了填」。

## 4. 第 2 节「数据缺口与未评估项」的结构

本节由四个**互相独立**的子块组成，各自为空时显示「无」：

| 子块 | 内容 | 空时 |
|---|---|---|
| 未评估规则表 | 规则 / 原因 / 缺失字段 / 来源模块 | `无` |
| 待补齐的证据表 | 目标 / 证据类型 / 证据 ID / 引用 | `待补齐的证据：无` |
| 被契约拒绝的结果表 | 来源 / `result_id` / 问题 | 整块省略 |
| 跨模块冲突列表 | 冲突描述 | 整块省略 |

本节开头有一段固定提示：

> 本节与「通过」**严格分区**。出现在本节的规则**没有被评估过** ——
> 缺失输入不等于合规（硬约束 H3）。

## 5. 第 3 节「需决策的发现」的渲染

每条发现一个三级标题 `### <target_ref> — <动作中文名>`，正文固定包含：

| 项 | 说明 |
|---|---|
| 结论 | `verdict（中文）` |
| 风险等级 | 5 档中文名 |
| 建议动作 | 动作中文名；`freeze_relist` / `escalate_legal` 追加「（需人工执行）」 |
| 理由 | 聚合结果的 `reason` 原文 |
| 置信度 | `signal` / `likely` / `confirmed` 的中文说明 |
| 需人工执行提示 | 仅 `human_only` 动作出现（H6） |
| 需人工判断 | `review_rationale` 原文 |
| 命中规则与来源表 | 规则 / 标题 / 命中字段 / 命中片段 / 来源层级 / 来源链接 |
| 证据引用表 | 证据 ID / 类型 / 已提供 / 引用 / 定位 / 备注（H5：只含引用） |

**来源层级用中文名显示**（`平台规则` / `法律规定` / `内部风控建议` /
`待核实` / `AI 推断` / `技术调研结论`）—— 这是章程 §1.2 的要求。

## 6. 第 4 节「待复核的发现」的渲染

一张表，列为：

```
目标 | 动作 | 结论 | 严重度 | 置信度 | 命中规则 | 理由
```

「理由」列截断到 160 字符 —— 完整理由在 JSON 汇总里。

## 7. 第 5 节「逐商品结果」的渲染

一张表，列为：

```
商品 | SKU | 店铺 | 结论 | 动作 | 严重度 | 置信度 | 命中规则 | 未评估
```

- 「商品」列用 `target_ref`。
- 「SKU」「店铺」来自 `SkillInput.products[]` 中 `product_id` 相同的条目；
  找不到时显示 `—`。
- 「命中规则」是去重后的 `rule_id` 逗号分隔；无命中显示 `—`。
- 「未评估」是该目标的 `unevaluated` 条数（数字，不是文字）。

## 8. 第 6 节「已查阅规则」的渲染

一张表，列为：

```
规则 | 标题 | 类别 | 严重度 | 动作 | 来源层级 | 核查日期 | 来源链接
```

- **类别 / 严重度 / 动作 / 核查日期**来自规则库（`rules/*.json`），
  **原样透传**，本模块不重新判定。
- **来源层级 / 来源链接**优先取 `rule_refs[]` 里上游模块给出的值
  （上游可能比规则库更新），缺失时回落到规则库。
- 规则库里没有的规则（上游自带的临时规则）仍然列出，缺失字段显示 `—`。

## 9. 空值表达

| 情况 | 表达 |
|---|---|
| 无数据缺口 | `无` |
| 无需决策的发现 | `无` |
| 无待复核发现 | `无` |
| 无待补齐证据 | `待补齐的证据：无` |
| 表格单元格无值 | `—` |

**不得**用空白或 `-` 省略表格单元格。

## 10. 硬约束节

报告末尾**必须**包含已执行的硬约束清单：

```markdown
## 硬约束
- H1 IP 类结论恒为 signal 且需人工复核 — ✅
- H2 阻断类动作仅来自 platform_official/law 的 active 规则 — ✅
- H3 输入缺失标记未评估，不计为通过 — ✅
- H4 引文逐字核验 — ✅
- H5 证据只存引用 — ✅
- H6 冻结与法务升级为人工专属 — ✅
```

实现时用**基于本次数据的数字**填进括注（例如「本次 2 条阻断类动作均已核验
来源层级」），而不是复制一段固定文本 —— 数字必须与摘要节一致。

## 11. Markdown 转义

| 字符 | 处理 |
|---|---|
| `|` | 转义为 `\|` |
| 换行 | 替换为空格 |
| 空字符串 | 显示 `—` |

表格单元格内的原文因此不会被表格结构破坏。
