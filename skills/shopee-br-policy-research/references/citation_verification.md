## 1. 为什么必须有这道关

规则库里的每条规则都声称「依据某来源的某段原文」。如果引文是编的或改写的，
整套规则库的公信力就没了 —— 而且**下游模块会照着它产生阻断性结论**。

因此：**引文必须逐字出现在抓取件中。** 这是硬约束 **H4**。

```
env -u LD_LIBRARY_PATH python3 tools/verify_citations.py
```

当前：**50/50 逐字核验通过，0 失败。**

## 2. 核验算法

`tools/verify_citations.py` 对每条规则的 `source_excerpt`：

1. 载入 `research/raw/*.txt` 全部抓取件
2. 归一化：弯引号/破折号/不换行空格 → ASCII；折叠连续空白；转小写
3. 在每个抓取件中查找该归一化文本
4. 命中 → 报告命中的**抓取件名**（便于人工确认引文来自正确的文档）
5. 全部未命中 → 该规则核验失败

### 2.1 宽松匹配（`loose`）

抓取件里混着页面 UI 文本（`..., clique aqui.`），逐字比对时引文结尾的
逗号在原文里可能是句号。因此除了严格比对，还有一层「去句末标点」的宽松比对：

| 保留 | 去除 |
|---|---|
| 每一个字母、数字、词 | `,` `.` `;` `:` |
| 词间空格 | 首尾空白 |

**只去句末标点，其余一个字符都不放过** —— 改写仍然会失败。

> 宽松匹配**不是**「差不多就行」。它只解决标点差异，不解决文字差异。

## 3. 什么算「逐字」

| 情况 | 结果 |
|---|---|
| 引文与原文完全一致 | ✅ |
| 引文末尾标点不同（逗号 vs 句号） | ✅（宽松匹配） |
| 引文少了句尾「Gera ponto de penalidade.」 | ✅（引文是原文的**子串**即可） |
| 引文把葡语单词换成了中文/英文 | ❌ |
| 引文调换了两个词的顺序 | ❌ |
| 引文对原文做了同义改写 | ❌ |
| 引文有原文没有的额外限定 | ❌ |

**引文可以是原文的片段**（不必是完整段落），但**不能改字**。

## 4. 常见失败原因与处置

| # | 原因 | 症状 | 处置 |
|---|---|---|---|
| 1 | 引文是**转述**而非原文 | 核验报「not found」 | 回到抓取件里**逐字复制**原文 |
| 2 | 原文里的换行被引文写成空格 | 核验失败 | 归一化会处理；仍失败说明中间有别的字符 |
| 3 | 特殊字符不同（`–` vs `-`、弯引号） | 核验失败 | 归一化会处理；仍失败就复制原文 |
| 4 | 引文来自**没抓到的**页面 | 核验失败 | 抓取该页面；或改用已抓到的来源 |
| 5 | 页面更新，原文变了 | 核验失败 | 重新抓取 → 更新引文 → 更新 `last_verified` |
| 6 | 抓取件是空占位（20 字节） | 核验失败 | 重抓。`tools/check_sources.py` 会先报出来 |
| 7 | 引文跨越了页面中间的分页符 | 核验失败 | 缩短引文到同一段内 |

> **第 6 类是历史真实发生过的问题**：5 个来源的抓取报告记着 `text_chars: 20`，
> 而文件后来被重抓成了 5KB–36KB，但报告没更新。
> 现在 `tools/check_sources.py` 会比对报告与实际并报「报告已过期」。

## 5. 引文写进规则

`contracts/rule_envelope.schema.json` 的 `source` 结构：

```json
{
  "tier": "platform_official",
  "url": "https://seller.br.shopee.cn/edu/article/5139",
  "excerpt": "[317] Anúncio proibido para armas de fogo, tasers, munições e coletes à prova de balas. Severidade: Extrema. Gera ponto de penalidade.",
  "last_verified": "2026-10-27",
  "article_id": "5139",
  "platform_code": "[317]"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `tier` | ✅ | 来源层级 |
| `url` | ✅ | 指向具体页面 |
| `last_verified` | ✅ | 核查日期（ISO 8601） |
| `excerpt` | | 逐字引文 —— 核验的就是它 |
| `article_id` | | 平台文章编号（便于定位） |
| `platform_code` | | 平台违规码 |

> `article_id` 与 `platform_code` **不是必需**，但强烈建议填 ——
> 它们让「从一条结论回到平台原文」变成一次查表，而不是一次搜索。

## 6. 核验不通过怎么办

**不要**把引文改写成「看起来对」的版本 —— 那是编造。

按优先级：

1. **引文确实存在，只是格式差异** → 调整标点/空白后重试
2. **引文在别的抓取件里** → 核验输出会点名是哪个文件；把 `source.url` 改对
3. **原文确实没有这句话** → 规则的内容是错的：
   - 若规则本身对但引文选错了 → 换一段确实存在的原文
   - 若规则本身是推断出来的 → `source.tier` 改为 `unverified`，`status` 改为 `draft`，
     **不得**标 `active`
4. **来源没抓到** → 抓取；抓不到则该规则不能用这个来源支撑

## 7. 全库核验的分工

| 工具 | 抓什么 |
|---|---|
| `verify_citations.py` | 引文**逐字**出现在抓取件中（防编造） |
| `check_sources.py` | 来源清单 ↔ 抓取件 ↔ 抓取报告三者一致；失败来源不被引用 |
| `check_rule_regex.py` | 规则正则可编译；`requires_input` 自指；数值算子误用 |
| `verify_fixtures.py` | 夹具声明的期望是否成立（正例真命中、反例真不命中） |

四者互补：**引文核验管「内容是否属实」，来源核验管「证据是否可用」，
正则核验管「规则是否可执行」，夹具核验管「规则是否有效」。**
